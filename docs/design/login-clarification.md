## 3. 可行方案对比

### 方案 A：LeanCloud 内置用户系统（推荐 ✅）

**核心思路**：利用已集成的 LeanCloud BaaS 的用户管理能力，在静态页面中实现登录/注册。

| 维度 | 评估 |
|------|------|
| **技术栈匹配** | ✅ 已集成 LeanCloud SDK，零额外依赖 |
| **实现复杂度** | 低 — 前端 JS 调用 LeanCloud User API |
| **安全性** | 中 — Token 存储在 localStorage，需配合 HTTPS |
| **维护成本** | 低 — LeanCloud 托管用户数据 |
| **费用** | LeanCloud 免费额度通常够用 |

**流程概要**：
```
[登录页] → AV.User.logIn(username, password) → 获取 sessionToken → 存储 localStorage
→ 后续请求携带 sessionToken 验证身份 → 受保护页面校验登录态
```

### 方案 B：第三方 Auth 服务（Auth0 / Firebase Auth）

| 维度 | 评估 |
|------|------|
| **技术栈匹配** | ⚠️ 需引入新 SDK |
| **实现复杂度** | 中 — 需注册第三方服务、配置回调 |
| **安全性** | 高 — 成熟的身份认证方案 |
| **维护成本** | 低 — 托管服务 |
| **费用** | 免费额度有限，高流量可能收费 |

### 方案 C：纯前端密码门（简易方案）

| 维度 | 评估 |
|------|------|
| **技术栈匹配** | ✅ 纯 JS 实现 |
| **实现复杂度** | 极低 — 前端密码比对 |
| **安全性** | ❌ 极低 — 密码硬编码或可被查看 |
| **适用场景** | 仅适合低安全需求的简单保护 |

## 4. 推荐方案：方案 A — LeanCloud 用户系统

### 4.1 选择理由

1. **零新依赖**：LeanCloud SDK 已集成，无需注册新服务
2. **最小改动**：仅新增登录页面 + 认证 JS 模块，不影响现有博客功能
3. **可扩展**：后续可基于此扩展评论系统、会员系统
4. **行业惯例**：静态站点 + BaaS 用户系统是标准做法

### 4.2 功能范围定义

**本期范围（MVP）**：
- [x] 登录页面（`/admin/login.html`）
- [x] 登录表单（用户名 + 密码）
- [x] LeanCloud 用户认证
- [x] 登录态管理（sessionToken 存储与校验）
- [x] 管理后台入口页（登录后可见）
- [x] 登出功能

**不在本期范围**：
- 用户注册（博主账号由 LeanCloud 控制台手动创建）
- 密码找回
- 第三方登录（GitHub/微信等）
- 多用户/权限管理

| `css/login.css` | 登录页样式 |

### 4.5 数据流设计

```
登录流程：
  用户输入 username + password
  → auth.js 调用 AV.User.logIn()
  → LeanCloud 返回 { sessionToken, user }
  → 存储 sessionToken 到 localStorage
  → 跳转管理后台

鉴权守卫：
  页面加载 → auth.js 读取 localStorage 中的 sessionToken
  → AV.User.become(sessionToken)
  → 成功：渲染受保护内容
  → 失败：跳转登录页

登出流程：
  点击登出 → AV.User.logOut()
  → 清除 localStorage
  → 跳转登录页
```

### 4.6 安全考量

| 风险 | 缓解措施 |
|------|---------|
| XSS 窃取 token | 使用 HttpOnly 不可行（静态站点），依赖 CSP 头 + 输入过滤 |
| Token 过期 | sessionToken 默认有效期为 1 年，或配置 LeanCloud 短期过期 |
| 暴力破解 | LeanCloud 内置登录失败次数限制 |
| 页面直接访问 | 管理后台页面加载时执行鉴权守卫，未登录立即跳转 |

| 风险/待确认 | 影响 | 当前假设 |
